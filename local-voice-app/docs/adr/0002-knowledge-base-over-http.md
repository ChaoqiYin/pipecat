# 知识库由应用直连本机 HTTP API，而不是经 MCP 接入

`llm_wiki` 桌面应用在 `127.0.0.1:19828` 暴露一个 token 保护的 HTTP API。应用直接请求它：检索在应用自己的代码里完成，取回整页正文，再交给模型改写。

## 考虑过的其他做法

- **经 MCP 接入**（对方自带的 MCP server）：协议层能把「换服务器位置、换实现」变成纯配置变更，这是它的价值。代价是它丢正文——那个 MCP server 的搜索结果里没有整页正文这一项，模型只拿得到 `snippet`，而片段是在行中间截断的，答案所在的那一行常常不在其中。模型于是反复改写查询重搜，一次提问触发多轮检索。知识库回答所依据的正是正文，所以这一层不能丢。
- **自己写一个 MCP server 包住 llm_wiki**：能同时拿到协议抽象和正文，但那层适配要由本应用维护，而对方已经提供 MCP server，重复造一层不划算。
- **做成框架里的服务**（像 `KeenableWebSearch` 那样包一个托管 MCP server）：会把单一供应商的知识放进框架，而这不是框架的职责。

## 后果

- llm_wiki 的地址、鉴权头和路由写在应用里。换一个知识库不是改配置，是加一个实现——`KnowledgeBase` 是为此留的接缝，目前只有一个实现。
- 本机使用时，bot、浏览器客户端和知识库桌面应用必须同机：HTTP API 只监听回环。远程部署要另找出路。
- 不需要 `mcp` 可选依赖。
- 检索时机只在调用时：会话建立不连知识库，装配期不因它是否可用而受影响，连不上表现为一次「查不到」而不是会话起不来。
- 知识库查询工具内部做「搜索 → 读最相关的一两页 → 返回正文」，对模型仍是一次调用。搜索只用来定位页面，不是答案来源。
